We cut cold-start latency 63% by rewriting our edge router in Rust

The old router was fine until it wasn’t. Here is the profiling trail, the three rewrites that didn’t work, and the boring architecture that finally did.

Mara Ostrowski
Staff Engineer, Edge
Jul 12, 202611 min readUpdated after launch

On this page

  1. The symptom
  2. Where the time went
  3. Three rewrites that failed
  4. The architecture that worked

  6. What we’d do differently

The symptom

Every request that hit a freshly-scheduled edge worker paid a tax. Not a huge one — about 180 ms on the median cold path — but at our volume that tax showed up as a fat bump on the p99 latency chart every time a region scaled up. Warm requests were fine. Cold ones were embarrassing.

The router was a small Node service: parse the request, look up a route in an in-memory table, forward to origin or serve from cache. Perfectly reasonable code. The problem was never the steady state — it was the first request after a worker booted.

Definition

“Cold start” here means the wall-clock time from a worker receiving its first request to that request being fully served — including any lazy initialization the runtime does on the way.

Where the time actually went

Before touching a line of code we did the boring, correct thing: we measured. A flame graph of the cold path is worth a thousand hunches. We wrapped the hot handler in a sampling profiler and shipped it to 1% of traffic for a day.

The result was humbling. Route lookup — the part we’d assumed was slow — was under a millisecond. The real cost was runtime warm-up: JIT compilation of the request path, and re-hydrating a 4 MB routing table from JSON on every boot.

profile.sh 
1# sample the cold path, fold, and render a flame graph2perf record -F 999 -g -- ./router --cold-once3perf script | stackcollapse-perf.pl > out.folded4flamegraph.pl out.folded > cold.svg

Here is the shape of what came back — abbreviated, but the ratios are real:

# cold path, median of 200 samples
route.lookup .......... 0.8 ms   (0.4%)
jit.warmup ............ 96.0 ms  (53.3%)
table.hydrate ........ 61.0 ms  (33.9%)
tls.handshake ........  18.0 ms  (10.0%)
------------------------------------------
total ................ 180.0 ms

“We were about to optimize the one part of the system that was already fast.”

// note-to-self, day two of the investigation

Three rewrites that didn’t work

Knowing where the time went didn’t hand us a fix. We tried three things, in order, and each taught us something before it fell over.

  1. Cache the parsed table on disk. Shaved the hydrate cost but reintroduced it as a slow fs.read on the first request. Net wash.
  2. Precompile with a snapshot. Killed JIT warm-up in benchmarks, but the snapshot went stale on every deploy and the tooling fought us daily.
  3. Move the table to a sidecar. Great isolation, terrible latency — we’d traded warm-up time for a network hop on the exact path we were trying to speed up.
Watch out

Every one of these looked great in a microbenchmark. Microbenchmarks don’t deploy, restart, or serve real traffic — measure the whole cold path or you’ll optimize the wrong thing twice.

The boring architecture that did

The fix was not clever. We rewrote the router in Rust, embedded the routing table into the binary at compile time as a perfect-hash map, and let the OS memory-map it. No JIT, no JSON, no hydrate step — the table is simply there the instant the process starts.

router.rs 
1// table baked in at build time — zero startup cost2static ROUTES: phf::Map<&str, Origin> = phf_map! {3    "/api" => Origin::Api,4    "/img" => Origin::Assets,5};67pub fn route(path: &str) -> Origin {8    ROUTES.get(path).copied().unwrap_or(Origin::Origin)9}

The handler itself stayed almost identical to the Node version — the win was entirely in what didn’t happen at boot. We kept the same cache semantics and the same origin-fetch fallback so behavior was byte-for-byte compatible.

Takeaway

Reach for a compile-time constant before a runtime cache. The fastest hydrate step is the one that never runs.

The numbers

We rolled it out region by region behind a flag, comparing cold-path p50 and p99 against the Node baseline on identical hardware.

results.md 
1metric            node      rust     delta2----------------------------------------------3cold p50        180 ms   67 ms    -63%4cold p99        340 ms  121 ms    -64%5warm p50          9 ms    6 ms    -33%6rss at boot      92 MB   11 MB    -88%

The memory drop was the surprise bonus. An 11 MB resident set meant we could pack more workers per node, which meant fewer cold starts in the first place — a small virtuous cycle.

What we’d do differently

Two things. First, we’d have profiled on day one instead of day two — the two microbenchmark detours cost us a week of chasing the wrong bottleneck. Second, we’d have written the compatibility test suite before the rewrite, not alongside it; catching the one header-casing difference early would have saved a nervous canary.

Would we reach for Rust again? For a hot, latency-critical path with a stable interface — yes, without hesitation. For a service that changes shape every sprint, the Node version was the right call for years. Boring is contextual.
